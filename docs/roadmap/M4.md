# M4: テナントコンテキスト注入（`withTenant` ヘルパ）

## 狙い

Hono からまだ呼ばれていない状態で、

```ts
await withTenant(tenantId, async (tx) => tx.select().from(postsTable));
```

が **「テナント分離されたクエリ」を発行する状態** を作る。M5 でこの関数を Hono
ハンドラから呼べるようにするための土台。

## 事前知識：なぜ `SET LOCAL` でないと事故るか

### `SET` と `SET LOCAL` の有効範囲

| 構文 | 効果が及ぶ範囲 |
| --- | --- |
| `SET app.tenant_id = 'T1'` | **セッション**（接続が閉じるまで） |
| `SET LOCAL app.tenant_id = 'T1'` | **トランザクション**（`COMMIT` / `ROLLBACK` で消える） |

### プール再利用での汚染

`pg.Pool` はリクエスト終了時にコネクションを物理的に切らずプールへ返す。**セッション
レベル `SET`** だと次の利用者にコンテキストが残る：

```text
リクエスト A: SET app.tenant_id = 'T1'  → 処理 → 接続をプールに返す
リクエスト B: 同じ接続を再利用、SET 忘れ → SELECT
              ↓
              current_setting('app.tenant_id') == 'T1' のまま
              → B が T1 のデータを読んでしまう（コネクション汚染 / セッション残留）
```

**`SET LOCAL`（あるいは `set_config(_, _, true)`）** をトランザクション内で使えば、
`COMMIT` の瞬間に効果が消えるのでプール再利用されても次に漏れない。

### Aurora / RDS Proxy の transaction-mode pooling

```ts
await db.execute(sql`SET app.tenant_id = 'T1'`);   // (1)
const posts = await db.select().from(postsTable);   // (2)
```

トランザクションモードのプール越しだと **(1) と (2) が同じ物理接続上で実行される
保証はない**。安全に動かすには、(1) と (2) を**同一トランザクションに束ねる**しかない。
これが「`withTenant` が `db.transaction` のラッパとして実装される」根拠。

## 採用した設計判断

| # | 判断 | 採用 | 理由 |
| --- | --- | --- | --- |
| 1 | `Pool` / `Drizzle` クライアントのライフサイクル | A: アプリ全体で 1 個 | `Pool` を毎回作ると接続が無限増殖する。プロセス起動時に 1 個生成、`graceful shutdown` で `pool.end()` |
| 2 | テナント注入のヘルパ API 形 | A: 高階関数 `withTenant(id, callback)` | `AsyncLocalStorage` と比べて挙動が直列で読みやすく、依存も最小。スコープ漏れの心配がない |
| 3 | `SET LOCAL` の構文 | B: `set_config('app.tenant_id', $1, true)` 関数形 | パラメータ化（SQL injection 安全）。Drizzle の `sql` テンプレートに組み込みやすい |
| 4 | `tenant_id` のバリデーション位置 | A: ヘルパ入口で Zod 検証 | DB に届く前に弾く。後段の `current_setting(...)::uuid` キャスト失敗より UX が良い |
| 5 | ファイル配置 | B: 役割別に分割 | `client.ts`（接続）/ `with-tenant.ts`（注入ヘルパ）/ `schema/`（テーブル定義）と分けてエントリを単機能に保つ |

## 実装の構成要素

### `src/db/client.ts`

```ts
const connectionString = process.env.APP_DATABASE_URL;
if (!connectionString) throw new Error('env APP_DATABASE_URL is not set');

export const pool = new Pool({ connectionString, max: 10 });
export const db = drizzle({ client: pool, schema, casing: 'snake_case' });
```

押さえどころ：

- `APP_DATABASE_URL` を**起動時に検証**してエラー早期化
- 接続は `app_user`（`migrator` でも `postgres` でもない）。これによりこのクライアント
  経由の全クエリが RLS の対象になる
- **`casing: 'snake_case'`** をランタイムでも指定。`drizzle.config.ts` の指定は
  drizzle-kit のマイグレーション生成にしか効かないので、書き忘れると `db.select()`
  が `"createdAt"` を発行して `"column does not exist"` で死ぬ
- `pool` も named export。`graceful shutdown` でプロセス終了時に `pool.end()` する用途

### `src/db/schema/index.ts`（barrel）

```ts
export * from "./tenants";
export * from "./users";
export * from "./posts";
```

`drizzle({ schema })` に渡すための統合 export。drizzle-kit の glob 設定とは別系統で必要。

### `src/db/with-tenant.ts`（本マイルストンの主役）

```ts
export const tenantIdSchema = z.uuidv7('Invalid UUIDv7');

type Tx = Parameters<Parameters<typeof db.transaction>[0]>[0];

export async function withTenant<T>(
  tenantId: string,
  callback: (tx: Tx) => Promise<T>,
): Promise<T> {
  const validatedTenantId = tenantIdSchema.parse(tenantId);

  return await db.transaction(async (tx) => {
    await tx.execute(
      sql`SELECT set_config('app.tenant_id', ${validatedTenantId}, true)`,
    );
    return await callback(tx);
  });
}
```

押さえどころ：

- `tenantIdSchema` を **named export**（M5 でミドルウェアからも再利用）
- `z.uuidv7('Invalid UUIDv7')` は v7 厳格 + 明示メッセージ。`z.string().uuid()` だと
  v4 も通ってしまう
- `Tx` 型は `Parameters<...>` で抽出。Drizzle の `PgTransaction<...>` を直書きすると
  深い型操作になるので推論に任せる
- `${validatedTenantId}` は Drizzle の `sql` テンプレート内で**パラメータ化**される
  （SQL injection 安全）
- `set_config(_, _, true)` の第 3 引数 `true` が `IS_LOCAL` 相当
- `callback` が throw すると `db.transaction` が自動 ROLLBACK し、`SET LOCAL` の効果も消える

## 動作確認 (vitest 統合テスト)

`tests/db/with-tenant.test.ts` で 6 シナリオ：

| # | 検証 | 期待 |
| --- | --- | --- |
| 1 | T1 で `posts` を取得 | 2 件（Alice / Bob） |
| 2 | T2 で `posts` を取得 | 1 件（Carol） |
| 3 | T1 → T2 → T1 の連続呼び出し | 各回で正しい件数（プール再利用が漏らさない） |
| 4 | 不正な UUID で呼ぶ | `ZodError` でスロー（DB に到達しない） |
| 5 | 形式は v7 だが存在しない tenant id | 0 件返る（エラーではなく RLS の正常動作） |
| 6 | DANGER characterization | セッション SET の汚染を**故意に再現** |

シナリオ 6 は `withTenant` を経由しない安全実証ではなく **「もし `set_config(_, _, false)`
だったらどう壊れるか」を見せる対照実験**。`max: 1` の隔離プールを別途作って、
`Request A: SET, Request B: SELECT` の流れで B 側に T1 のコンテキストが残ることを assert する。
これが残っていれば、将来コードが「`SET LOCAL` をやめて `SET` に変えた」変更に対する
ガードレールになる（変更すると安全パステストが「壊れずに通る」のに DANGER テストが
壊れる）。

`beforeAll` で `ADMIN_DATABASE_URL` 経由（SUPERUSER）に `src/db/seeds/dev.sql` を
流して fixture を初期化。`afterAll` で `pool.end()` してプロセスをクリーンに終了。

## 詰まりやすいポイント

- **`schema` を渡し忘れる**：`drizzle({ client: pool })` だけだと型推論が弱い。`{ client, schema }` 必須。
- **`casing: 'snake_case'` の渡し忘れ**：`drizzle.config.ts` の指定は migration 生成にのみ効くので、ランタイムにも明示しないと `db.select()` がキャメルケース列名を発行する。
- **`Tx` 型の手書き**：`PgTransaction<...>` を直書きすると深くなる。`Parameters<Parameters<typeof db.transaction>[0]>[0]` で推論に乗せる。
- **`APP_DATABASE_URL` のロール一致**：`.env` の `app_user_password` と `0002_create_roles.sql` のハードコードが一致しないと認証エラー。
- **smoke test を ADMIN で実行しない**：`postgres` は SUPERUSER で RLS 素通り → 全件見えてしまい検証にならない。
- **`pool.end()` の呼び忘れ**：smoke test / vitest の `afterAll` で呼ばないとプロセスが終了しない。
- **vitest の seed パス**：`tests/db/with-tenant.test.ts` から見ると `../../src/db/seeds/dev.sql`。ファイル配置を変えたときに気付きにくい。

## このマイルストンで得られた言語化

- **`pg.Pool` のライフサイクル**：アプリ全体で 1 個、起動時に作って終了時に `pool.end()`。
- **Drizzle の `transaction()`**：自動 `BEGIN` / `COMMIT` / `ROLLBACK`。`callback` 引数 `tx` が同一接続を保持するので、`set_config` と本クエリが同じ接続上で確実に実行される。
- **`set_config('app.tenant_id', value, true)`**：`SET LOCAL` のパラメータ化版。SQL injection 安全 + tx スコープ。
- **Zod での UUID 検証位置**：DB 到達前に弾けば、`current_setting()::uuid` キャスト失敗より明示的なエラーが出せる。後で M5 のミドルウェアからも同じ schema を再利用できる。
- **DANGER characterization test の価値**：「これが起きうる」を**コードで再現**しておくと、後続の変更で安全性が壊れた瞬間に発覚する。コメントで書くより強い証拠。
