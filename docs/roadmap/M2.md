# M2: 3 ロール構成と権限分離

## 狙い

スキーマ作成までは `postgres`（SUPERUSER）で済ませていた状態から、
**`postgres` / `migrator` / `app_user`** の 3 ロール構成に切り替える。

ねらいは 2 つ：

1. **アプリ接続から DDL を打てなくする**（最小権限）
2. **テーブル所有者ですら RLS をバイパスしないことを観察する土台**を作る  
   → 所有者を `migrator` に移してから M3 で `FORCE ROW LEVEL SECURITY` を有効化すると、
   所有者の挙動が変わる「見せ場」が成立する

## ロール設計

| ロール | 属性 | 用途 |
| --- | --- | --- |
| `postgres` | SUPERUSER | DB 作成と 0002 の bootstrap、緊急対応のみ |
| `migrator` | LOGIN, NOSUPERUSER, NOBYPASSRLS | スキーマ DDL 実行とテーブル所有 |
| `app_user` | LOGIN, NOSUPERUSER, NOBYPASSRLS | アプリ実行時の CRUD 接続（M3 以降は RLS 適用対象） |
| `app_readwrite_group` | NOLOGIN | 権限を束ねるグループロール（後述） |

`migrator` と `app_user` どちらにも **`NOBYPASSRLS` を明示**する。デフォルトでは付かないが、
`BYPASSRLS` が付いているとポリシーが完全に無視されるので、明示することで意図を残す。

### グループロールを噛ませる理由

権限を `app_readwrite_group` という LOGIN なしロールに集約し、それを `app_user` と
`migrator` に `GRANT` する。直接 `app_user` に `GRANT` しても動くが、

- 将来「読み取り専用ロール」など別ログインロールを足したくなったとき、グループに
  `GRANT` するだけで済む
- 権限の付与/剥奪を 1 箇所で管理できる

という拡張性のため。`migrator` にも同じグループを付けているのは、所有者は所有権で
CRUD できるが、明示的に GRANT も持たせておくと debug 時の挙動が読みやすいから。

## 0002_create_roles.sql の構成

冒頭コメントで **「このマイグレーションは `postgres` で適用すること、これ以降は
`migrator` で実行すること」** を明記してある。

| セクション | 内容 |
| --- | --- |
| 1. ログインロール作成 | `app_user` / `migrator` を `DO $$ ... $$` で冪等に作成 |
| 2. グループロール作成 | `app_readwrite_group` |
| 3. 所有権移譲 | `tenants` / `users` / `posts` / `__drizzle_migrations` / `set_updated_at()` を `migrator` に |
| 4'. `PUBLIC` 剥奪 | `REVOKE CREATE ON SCHEMA public FROM PUBLIC` |
| 4. グループへ GRANT | `CONNECT` / `USAGE` / 全テーブルへの CRUD / sequences `USAGE,SELECT` |
| 5. デフォルト権限 | **`FOR ROLE migrator`** を明示してテーブル / sequences / functions を自動付与 |
| 6. グループ割り当て | `GRANT app_readwrite_group TO app_user, migrator` + `migrator` に `USAGE, CREATE ON SCHEMA public` |

### 押さえどころ

#### 所有権移譲は `REASSIGN OWNED BY` を使わない

`REASSIGN OWNED BY postgres TO migrator` は副作用が広すぎ、`postgres` 所有のシステム
オブジェクトまで巻き込む。**個別に `ALTER TABLE/FUNCTION ... OWNER TO migrator;`** で
明示する。

#### `set_updated_at()` 関数も移譲する

トリガが `migrator` 所有テーブルから `postgres` 所有関数を呼ぶ形になると、後の関数
更新時に権限警告が出るケースがある。テーブルと関数の所有者を揃えるのが事故が少ない。

#### `__drizzle_migrations` の所有者も `migrator` に

`drizzle-kit migrate` がこのテーブルへ書き込むので、所有権が `postgres` のままだと
`migrator` 接続で次のマイグレーションが流せない。

#### `REVOKE CREATE ON SCHEMA public FROM PUBLIC`

PG 14 以前の伝統的なデフォルトでは `public` スキーマの `CREATE` が `PUBLIC`（全ロール
の暗黙メンバー）に付いている。これを剥奪しないと、`app_user` 接続で `CREATE TABLE`
が通ってしまう。M3 で RLS を入れる前に塞いでおく。

#### `ALTER DEFAULT PRIVILEGES FOR ROLE migrator`

これが **3 ロール構成での新しい必須事項**。デフォルト権限は「誰がそのオブジェクトを
作ったか」に紐づく。2 ロール構成（postgres がテーブル作成者）なら不要だったが、
所有者が `migrator` に変わったので **`FOR ROLE migrator` を明示**しないと、
将来 `migrator` が新規テーブルを作っても `app_readwrite_group` に権限が付かない。
これを忘れるのが典型的な事故。

## 適用手順（順序が重要）

```sh
# Step 1: drizzle.config.ts は ADMIN_DATABASE_URL を参照したまま、
#         postgres で 0002 を適用する
pnpm drizzle-kit migrate

# Step 2: drizzle.config.ts を MIGRATOR_DATABASE_URL 参照に書き換える

# Step 3: .env / .env.example に 3 つの接続文字列を揃える
#   ADMIN_DATABASE_URL    = postgres://postgres:.../rls_poc
#   MIGRATOR_DATABASE_URL = postgres://migrator:.../rls_poc
#   APP_DATABASE_URL      = postgres://app_user:.../rls_poc
```

Step 1 と Step 2 を逆にすると、**まだ存在しない `migrator` ロールでログインを試みて失敗**する。

## 完了判定（psql で確認）

| # | 確認内容 | 期待 |
| --- | --- | --- |
| 1 | `\du` でロール属性 | `postgres` は SUPERUSER 等、`migrator` / `app_user` は属性空欄、`app_readwrite_group` は `Cannot login` |
| 2 | `\dt+` でテーブル所有者 | `tenants` / `users` / `posts` / `__drizzle_migrations` の Owner が `migrator` |
| 3 | `migrator` で `CREATE TABLE _scratch (id int)` | 通る（DDL 可能） |
| 4 | `app_user` で `CREATE TABLE _scratch (id int)` | `permission denied for schema public` |
| 5 | `app_user` で `SELECT count(*) FROM tenants` | 通る（CRUD 可能） |
| 6 | `pnpm drizzle-kit migrate`（`migrator` で実行） | `Already up to date` |

「ビフォー」状態の確認として、`app_user` で `SELECT * FROM posts` が **全テナント分
見える**ことも見ておくと良い（M3 で RLS が効くと見え方が変わる）。

## 詰まりやすいポイント

- **適用順を間違える**：Step 1（`postgres` で 0002 適用）→ Step 2（config 切り替え）の順を厳守。逆にすると認証エラー。
- **`ALTER DEFAULT PRIVILEGES FOR ROLE` の漏れ**：書かないと M3 以降の新規テーブルで `app_user` から見えない事故が後出しで発生。
- **`__drizzle_migrations` の所有権移譲忘れ**：次回以降の `drizzle-kit migrate` が書き込みに失敗する。
- **関数の所有権移譲忘れ**：`set_updated_at()` を `migrator` に移し忘れると、後で関数 `ALTER` の度に警告が出る。
- **パスワード不一致**：3 つの接続文字列の値と `0002_create_roles.sql` の `PASSWORD` がズレると認証エラー。
- **`DO $$ ... $$;` の終端セミコロン**：忘れると `drizzle-kit migrate` がパースエラーで止まる。

## このマイルストンで得られた言語化

- **bootstrap の段取り**：「鶏と卵」を `postgres → migrator` の二段ロケットで解く。本番でも繰り返し出てくるパターン。
- **`ALTER DEFAULT PRIVILEGES FOR ROLE` の必須性**：テーブル作成者が誰かで権限自動付与の宛先が決まる。
- **`REASSIGN OWNED BY` を避ける判断**：明示的 `ALTER ... OWNER TO` のほうがシステムオブジェクトを巻き込まず安全。
- **「所有者だが SUPERUSER ではない」ロールの存在意義**：M3 で `FORCE ROW LEVEL SECURITY` の挙動を観察する土台。
- **接続文字列の使い分け**：bootstrap / migration / runtime で別。本番では Secrets Manager で出し分け。
