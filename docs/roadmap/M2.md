  このマイルストンのゴール

  ▎ 3 つのロール（postgres / migrator / app_user）が存在し、テーブルの所有権が postgres
  ▎  から migrator に移譲されている。app_user
  ▎ で接続するとアプリケーションとして必要な権限を持っているが、所有者ではないので M3  
  ▎ で RLS が効く準備が整っている。さらに migrator で接続すると「所有者だが SUPERUSER

  作るもの

  1. src/db/migrations/0002_create_roles.sql（手書き SQL、postgres で実行）

  このマイグレーションは postgres
  で適用される最後のマイグレーションになります。冒頭にコメントで明記してください：

  -- 0002_create_roles.sql
  -- This migration MUST be applied as postgres (SUPERUSER).
  -- Subsequent migrations should be applied as migrator.
  -- DEV PASSWORDS ONLY. Production must use IAM auth or Secrets Manager.

  含める処理：

  1-a. ロールの冪等作成

  migrator と app_user を DO $$ ... $$; ブロックで IF NOT EXISTS 風に作成。それぞれ：  

- migrator：LOGIN PASSWORD '<dev_migrator_password>'、SUPERUSER / BYPASSRLS
  は付けない（明示的に NOSUPERUSER NOBYPASSRLS を書くと意図が伝わる）
- app_user：同上、別パスワード

  1-b. 既存オブジェクトの所有権を migrator に移譲

  REASSIGN OWNED BY postgres TO migrator は 副作用が広すぎる（postgres
  所有のシステムオブジェクトまで対象になる）ので、個別に ALTER を推奨：

  ALTER TABLE tenants OWNER TO migrator;
  ALTER TABLE users OWNER TO migrator;
  ALTER TABLE posts OWNER TO migrator;
  ALTER FUNCTION set_updated_at() OWNER TO migrator;
  ALTER TABLE __drizzle_migrations OWNER TO migrator;

- 既存テーブルすべてに ALTER TABLE ... OWNER TO migrator;
- set_updated_at()
  関数も移譲（テーブル所有者と関数所有者を揃えると、後でトリガー関連の権限事故が減る）
- __drizzle_migrations も移譲（次回以降のマイグレーション実行ロールが migrator
  になるため）

  1-c. app_user への GRANT

  GRANT CONNECT ON DATABASE rls_poc TO app_user;
  GRANT USAGE ON SCHEMA public TO app_user;
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;

  1-d. DEFAULT PRIVILEGES（ここが 3 ロール化で新たに重要）

  将来 migrator が新しいテーブルを作ったとき、その新規テーブルへのアクセス権を app_user
   に自動で付ける設定が必要。FOR ROLE migrator を明示：  

  ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

  ▎ 2 ロール構成のときは FOR ROLE 不要だった（postgres が同じくテーブル作成者）。3
  ▎ ロール構成では テーブル作成者が migrator に変わるため、FOR ROLE migrator
  ▎ を書かないと、新規テーブルへの app_user
  ▎ の権限が付かない。ここを忘れるのが典型的な事故です。

  1. drizzle.config.ts の更新（M2 の最後に切り替え）

  dbCredentials.url の参照を ADMIN_DATABASE_URL から MIGRATOR_DATABASE_URL
  に変更。これで以降の pnpm drizzle-kit migrate は migrator で実行されます。

  // 変更前
  url: process.env.ADMIN_DATABASE_URL!

  // 変更後
  url: process.env.MIGRATOR_DATABASE_URL!

  1. .env.example と .env

  3 つの接続文字列を持たせる：

# Superuser. Used only for the bootstrap migration (0002)

  ADMIN_DATABASE_URL=postgres://postgres:postgres@localhost:5432/rls_poc

# Migration runner. Owner of tables. Used by drizzle-kit from M2 onwards

  MIGRATOR_DATABASE_URL=postgres://migrator:CHANGE_ME@localhost:5432/rls_poc

  APP_DATABASE_URL=postgres://app_user:CHANGE_ME@localhost:5432/rls_poc

  .env.example は CHANGE_ME で、.env は 0002_create_roles.sql

  詰まりやすいポイント（先に共有）

- 適用順を間違える：drizzle.config.ts を migrator に切り替えてから 0002
  を流すと、migrator が存在しないので接続失敗。0002 適用 → config 変更の順を厳守。
- ALTER DEFAULT PRIVILEGES の FOR ROLE 漏れ：これがないと、M3
  以降で新規テーブルを足したときに app_user の権限が付かない。後で気づくと再起動級。
- __drizzle_migrations 所有権の移譲忘れ：このテーブルは drizzle-kit
  が自分で書き込む。所有者が postgres のままだと、migrator が drizzle-kit migrate
  実行時に書き込めない。
- CASCADE 系の所有権：set_updated_at() 関数を移譲しないと、トリガーが migrator
  所有テーブルから postgres 所有関数を呼ぶ形になり、後で関数 ALTER
  のたびに権限警告が出る場合がある。関数も移譲する。
- DO $$ ... $$; の終端：セミコロンを忘れると drizzle-kit migrate
  がパースエラーで止まる。
- パスワード一致：3 つの接続文字列のパスワードと、SQL
  のパスワードがズレると認証エラー。最初は素直に揃える。

  コミット粒度の提案

  feat(db): introduce migrator and app_user roles, transfer table ownership

- migrator: LOGIN, no SUPERUSER, no BYPASSRLS — runs DDL, owns all schema objects
- app_user: LOGIN, no SUPERUSER, no BYPASSRLS — runtime CRUD only
- Existing tables and set_updated_at() reassigned from postgres to migrator
- DEFAULT PRIVILEGES FOR ROLE migrator GRANT to app_user (handles future tables)
- Bootstrap migration applied as postgres; subsequent migrations run as migrator
