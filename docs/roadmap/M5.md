# M5: Hono ミドルウェア + posts CRUD + RFC 9457

## 狙い

M4 で作った `withTenant` を **HTTP リクエスト経由で呼び出せる** 状態にする。
`x-tenant-id` ヘッダから `tenant_id` を取り、ミドルウェアで検証し、CRUD ハンドラが
`withTenant` 経由で DB を操作する。**M3 で psql で確認した RLS の挙動が、curl
からも観察できる** 状態が完成のゴール。

エラーは **RFC 9457 Problem Details** で統一し、`Content-Type:
application/problem+json` で返す。

## スコープ

| 範囲 | 採用 |
| --- | --- |
| 認証 | `x-tenant-id` ヘッダ直接受け取り（本番想定の Cognito / JWT は対象外） |
| ルート | `posts` のみ 5 endpoint：`GET /` `GET /:id` `POST /` `PUT /:id` `DELETE /:id` |
| body / param 検証 | `@hono/zod-validator` を `ValidationError` に変換するラッパ経由で宣言的に |
| エラー応答 | `application/problem+json`（RFC 9457）、すべて `app.onError` を経由 |

## 採用した設計判断

### 判断 1：tenant_id の抽出・検証はどこでやるか

**A: ミドルウェアで抽出 + 検証**。ハンドラは検証済み値を `c.get('tenantId')` で取り出す。

各案の比較：

| 案 | 評価 |
| --- | --- |
| **A** ミドルウェアで抽出 + 検証 | ✅ fail-fast / 型保証 / 単一実装 |
| B 各ハンドラで抽出 + 検証 | 同じ処理が散在、修正箇所が増える |
| C ミドルウェアで抽出のみ、検証は `withTenant` 内に任せる | ❌ ハンドラ実行途中で `ZodError` が出る・`withTenant` を呼び忘れたら検証されない・`c.get('tenantId')` の型が `string \| undefined`・DB Pool 確保後に弾かれる |

A の「暗黙的」というデメリットは、Hono の `Variables: { tenantId: string }` を
ジェネリックに渡せば型補完で明示できるのでほぼ解消する。

### 判断 2：エラーハンドリング戦略

**A: `app.onError` で集約**。Laravel の `Handler::render` に相当する Hono の流儀。
全分岐を 1 箇所に集約し、`AppError` 派生 / `ZodError` / pg `42501` / `HTTPException` /
その他、を統一して RFC 9457 形式に変換する。

### 判断 3：リクエスト body / param の検証位置

**B: `@hono/zod-validator` を使う**。`zValidator('json', schema)` をハンドラの引数に
挟むだけで宣言的に検証でき、`c.req.valid('json')` が型推論される。失敗時は
`ValidationError` に変換するため、薄いラッパ `zv()` を介して使う。

### 判断 4：Hono のエントリポイント

**B: `app.ts`（factory）+ `server.ts`（起動）に分離**。

- `createApp()` を export しておけば、テスト時に `app.request()` で直接駆動できる
  （実 HTTP ポートが要らない）
- 将来 Lambda / Cloudflare Workers などへの移植も `server.ts` だけ差し替えればよい

### 判断 5：CRUD の最小スコープ

**A: `posts` のみ 5 endpoint**。`tenants` / `users` を CRUD 化すると RLS の挙動を
確認するには冗長。`posts` だけでも越境 INSERT 攻撃や existence-hiding を観察できる。

## エラー → HTTP status マッピング

クライアント観点の意味付け：

| シナリオ | status | 理由 |
| --- | --- | --- |
| `ZodError`（不正な UUID / 不正な body） | **400** | クライアント入力の形式エラー |
| RLS 違反（READ）：他テナント or 不在 | **404** | **存在の漏洩を防ぐため、404 で揃える**（403 だと「存在はする」を漏らす） |
| RLS 違反（WRITE）：越境 INSERT / UPDATE | **400** | クライアント入力の業務的エラー（pg 42501 を 400 に） |
| `x-tenant-id` ヘッダ不在 | **401** | 認証情報の不備（本番では JWT 不在に対応） |
| `x-tenant-id` の UUID 形式不正 | **400** | 入力の形式エラー |
| DB 接続エラー | **500** | サーバ責任（503 でも可） |

押さえどころ：

- **READ で見えない post と存在しない post を区別しない**。これが existence-hiding。
  「`/posts/{T2id}` を T1 が叩く」と「`/posts/{存在しない id}` を T1 が叩く」が
  同じ 404 を返すことで、別テナントに何が存在するかを推測されない。
- **`x-tenant-id` 不在は 401**。POC スコープなら 400 でも理解できるが、本番想定では
  JWT 不在 → 401 と整合する設計にしておく。
- **越境 WRITE は 400**。書き込み先が「見つからない」より「指定した参照が無効」の意。

## 実装の構成（実際に作ったもの）

原案では `src/errors.ts` をフラットに置く想定だったが、実装では HTTP 層を
`src/http/` 配下にまとめた：

```text
src/
├── app.ts                       Hono factory + onError（薄い I/O 層）
├── server.ts                    @hono/node-server エントリポイント
├── handlers/posts.ts            posts CRUD ハンドラ（5 endpoint）
├── http/
│   ├── status.ts                HttpStatus 定数（400/401/404/500/...）
│   ├── errors/index.ts          AppError 階層 + ProblemDetails 型 + 各種定数
│   ├── error-mapping.ts         任意の throw 値 → ProblemDetails の純粋関数
│   ├── response.ts              ItemResponse / ListResponse + ヘルパ
│   └── zod-validator.ts         @hono/zod-validator → ValidationError ラッパ
├── middleware/tenant-context.ts x-tenant-id 抽出 + 検証 + c.set
└── schemas/posts.ts             Zod スキーマ（param / create body / update body）
```

### `src/http/errors/index.ts`

`AppError`（abstract）+ 5 つの具象サブクラス（`ValidationError` /
`TenantHeaderMissingError` / `NotFoundError` / `RLSWriteError` / `DatabaseError`）。

各サブクラスは `type` / `code` / `title` / `status` をクラス固定で持ち、
`toProblemDetails(instance)` で RFC 9457 ボディに自己シリアライズする。

`ErrorType` / `ErrorCode` 定数と `PROBLEM_JSON_MEDIA_TYPE = 'application/problem+json'`
を export して、リテラル散在を防ぐ。

### `src/http/response.ts`（成功エンベロープ）

クライアントが「失敗は `body.code`、成功は `body.data`」だけを見れば良いように、
成功側にも envelope を強制する：

```ts
type ItemResponse<T> = { data: T };
type ListResponse<T> = { data: T[]; meta: { count: number } };
```

`item(post)` / `list(posts)` ヘルパでハンドラ側の記述を最小化。

### `src/http/error-mapping.ts`（純粋関数の分離）

`app.onError` を最初は if/else 集積で書いていたが、横断関心事（traceId 埋め込み、
エラーマスキング）の差し込み口を 1 箇所にしたかったので、**分岐ロジックだけを純粋
関数 `toProblemBody(err, instance)` に切り出した**：

| 入力 | 出力 |
| --- | --- |
| `AppError` 派生 | そのまま `toProblemDetails` に委譲 |
| `ZodError` | `ValidationError.fromZodError()` で変換 |
| pg エラーコード `42501` | `RLSWriteError`（cause チェーンを 5 段までたどる） |
| Hono `HTTPException` | `about:blank` + `HTTP_EXCEPTION` |
| その他 | `INTERNAL_SERVER_ERROR`（stderr へログ） |

`app.ts` の `onError` は **「URL → instance 抽出 → toProblemBody → problem+json
で返す」の 3 行**だけになった。Strategy パターンまでは砕かない（分岐 5 本では
indirection の cost が利益を上回る）。

### `src/http/zod-validator.ts`

`@hono/zod-validator` の薄いラッパ。失敗時に `ValidationError.fromZodError()` を
throw することで、すべての検証エラーが `app.onError` の同じパスを通る。
`fieldPathPrefix`（`json` / `param` / `header`）が `errors[].name` のプレフィクスになる。

### `src/middleware/tenant-context.ts`

```ts
export const tenantContext = createMiddleware<AppEnv>(async (c, next) => {
  const raw = c.req.header('x-tenant-id');
  if (!raw) throw new TenantHeaderMissingError();           // → 401

  const result = tenantIdSchema.safeParse(raw);
  if (!result.success) {
    throw ValidationError.fromZodError(result.error, {     // → 400
      detail: 'x-tenant-id header is not a valid UUIDv7',
      fieldPathPrefix: 'x-tenant-id',
    });
  }
  c.set('tenantId', result.data);
  await next();
});
```

`AppEnv = { Variables: { tenantId: string } }` を export しておくことで、ハンドラ側で
`c.get('tenantId')` が `string` として推論される。

### `src/handlers/posts.ts`

```ts
export const postsRoutes = new Hono<AppEnv>()
  .use('*', tenantContext)
  .get('/',         async (c) => /* list */)
  .get('/:id',      zv('param', postIdParamSchema), async (c) => /* item or 404 */)
  .post('/',        zv('json',  createPostBodySchema), async (c) => /* 201 */)
  .put('/:id',      zv('param', postIdParamSchema), zv('json', updatePostBodySchema), ...)
  .delete('/:id',   zv('param', postIdParamSchema), async (c) => /* 204 or 404 */);
```

`c.get('tenantId')` を取り出して `withTenant(tenantId, async (tx) => ...)` で
クエリ。0 件返ったら `throw new NotFoundError('post', id)`（→ 404）。

## 完了判定（curl 8 シナリオ）

```sh
T1=01900000-0000-7000-8000-000000000001
T2=01900000-0000-7000-8000-000000000002
T1_ALICE=01900000-0000-7000-8000-aaaaaaaaaaaa
T2_CAROL=01900000-0000-7000-8000-cccccccccccc
T2_POST=01900000-0000-7000-8000-ffffffffffff
```

| # | コマンド | 期待 |
| --- | --- | --- |
| 1 | `curl -i :3000/posts` | 401 `tenant-header-missing` |
| 2 | `curl -i :3000/posts -H "x-tenant-id: not-a-uuid"` | 400 `validation-error` |
| 3 | `curl :3000/posts -H "x-tenant-id: $T1"` | 200, posts 2 件 |
| 4 | `curl :3000/posts -H "x-tenant-id: $T2"` | 200, posts 1 件 |
| 5 | `curl -i :3000/posts/$T2_POST -H "x-tenant-id: $T1"` | 404 `not-found`（existence-hiding） |
| 6 | `curl -X POST :3000/posts -H "x-tenant-id: $T1" -H 'content-type: application/json' -d "{\"title\":\"hi\",\"userId\":\"$T1_ALICE\"}"` | 201, 作成された post |
| 7 | `curl -i -X POST :3000/posts -H "x-tenant-id: $T1" -H 'content-type: application/json' -d "{\"title\":\"x\",\"userId\":\"$T2_CAROL\"}"` | 400 `cross-tenant-violation` |
| 8 | `curl -i -X PUT :3000/posts/$T2_POST -H "x-tenant-id: $T1" -H 'content-type: application/json' -d '{"title":"hacked"}'` | 404 `not-found` |

すべてのエラー応答で `Content-Type: application/problem+json` が立っていること。
M6 でこれを Playwright + vitest による自動テストに置き換える。

## 原案からの主な乖離

設計の途中で生まれて原案にはない要素：

| 観点 | 原案 | 実装 |
| --- | --- | --- |
| ファイル配置 | `src/errors.ts` フラット | `src/http/errors/index.ts`（HTTP 層を 1 ディレクトリに集約） |
| 成功レスポンス | `c.json({ posts })` 手書き | `{ data, meta? }` envelope を `src/http/response.ts` に共通化 |
| エラー拡張ペイロード | RFC 例文に近い「トップレベルにスプレッド」案も検討 | 共通 `errors` バケツに統一（クライアント SSOT 重視） |
| エラー分岐の構造 | `app.onError` 内に if/else 集積 | 純粋関数 `toProblemBody` に分離（`src/http/error-mapping.ts`）し、`app.ts` は I/O のみ |
| 定数化 | リテラル散在 | `ErrorType` / `ErrorCode` / `PROBLEM_JSON_MEDIA_TYPE` に集約 |
| エントリポイント | `src/index.ts` を残す案も | `src/index.ts` 廃止、`src/server.ts` に統一 |
| `/health` | （言及なし） | M6 で Playwright `webServer` のヘルスプローブ用に追加 |

## 詰まりやすいポイント

- **`@hono/zod-validator` の戻り値**：POST/PUT body は `c.req.valid('body')` ではなく `c.req.valid('json')`。
- **`c.json()` は Content-Type を上書きする**：`application/problem+json` を返したいなら `c.body(JSON.stringify(...), status, { 'Content-Type': ... })`。
- **`Hono<AppEnv>` ジェネリック**：これを書かないと `c.get('tenantId')` が `unknown` になる。
- **`PgError.code` の取得**：Drizzle が `DrizzleQueryError` でラップするので `err.cause` を辿る必要がある。`error-mapping.ts` の `findPgErrorCode` が 5 段までチェーンを下る。
- **`AppError<TErrors>` のジェネリック不変性**：`AppError<undefined>` と `AppError<unknown>` は assignability で揺れる。`respondWithAppError(e: AppError<any>)` を **意図的に** 使うのが現実解（コメントで補強）。
- **factory パターンの罠**：`createApp()` を呼ぶ前に `pool` / `db` が初期化される（`client.ts` は import 時に走る）。テストで差し替えたいときは要工夫。

## このマイルストンで得られた言語化

- **認可情報の抽出位置**：ミドルウェアで一元化（fail-fast / 型保証 / 単一実装）。
- **RLS 違反の status code**：READ/WRITE で分ける。**READ は existence-hiding のため 404**、WRITE は入力エラー扱いで 400。
- **認証 vs 入力エラー**：401（認証情報なし）/ 403（権限なし）/ 400（入力不正）/ 404（不在 or 不可視）/ 500（サーバ責任）の使い分け。
- **エラー文字列を露出しない**：「行が見つからない」と「アクセス拒否」を返答で区別しない。レスポンスに detail を残しすぎないことで、攻撃者に推測材料を与えない。
- **共通エンベロープ**：成功 `{ data, meta? }` と失敗 `{ code, errors, ... }` の対称性。クライアントは `body.code` / `body.data` を見るだけで分岐できる。
- **責務の境界**：`app.ts` は I/O だけ、`error-mapping.ts` は分岐ロジックだけ、`errors/` は型と定数だけ、と切り分けると、横断関心事（traceId / マスキング / metrics）の差し込み口が分散しない。
