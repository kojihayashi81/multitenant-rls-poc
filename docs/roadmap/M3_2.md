  M3-3：実装範囲

  このマイルストンのゴール

  ▎ 3 テーブルに ENABLE + FORCE を入れ、各テーブルに 4
  ▎ つのポリシー（SELECT/INSERT/UPDATE/DELETE） を作成する。app_user セッションで SET
  ▎ LOCAL app.tenant_id = ... を行ってからクエリすると、自テナントの行しか見えず、越境
  ▎ INSERT/UPDATE はすべて DB レベルで弾かれる状態になる。

  作るもの
  
  1. src/db/migrations/0003_enable_rls.sql（手書き SQL）

  セクション分割推奨：

  1-a. RLS を有効化 + FORCE
  
  3 テーブルすべてに：

  ALTER TABLE <name> ENABLE ROW LEVEL SECURITY;
  ALTER TABLE <name> FORCE ROW LEVEL SECURITY;

  1-b. tenants のポリシー（4 つ）

  「自テナントの行だけ可視/編集/削除可」：

- SELECT: USING (id = current_setting('app.tenant_id')::uuid)
- INSERT: WITH CHECK (id = current_setting('app.tenant_id')::uuid)
- UPDATE: USING (id = ...) WITH CHECK (id = ...)
- DELETE: USING (id = ...)

  ▎ 注意：tenants は id 列がそのままテナント識別子。tenant_id
  ▎ 列は持っていない。なので述語は id = ... になります。users / posts は tenant_id =
  ▎ ...。

  1-c. users のポリシー（4 つ）
  
  「自テナント所属の user だけ可視/編集/削除可」：

- SELECT: USING (tenant_id = current_setting('app.tenant_id')::uuid)
- INSERT: WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid)
- UPDATE: 両方
- DELETE: USING

  1-d. posts のポリシー（4 つ、最も慎重に）

- SELECT: USING (tenant_id = current_setting('app.tenant_id')::uuid)
- INSERT: WITH CHECK に 越境チェックを含める
  tenant_id = current_setting('app.tenant_id')::uuid
  AND tenant_id = (SELECT tenant_id FROM users WHERE id = posts.user_id)
- または EXISTS 形：
  tenant_id = current_setting('app.tenant_id')::uuid
  AND EXISTS (
    SELECT 1 FROM users
    WHERE id = posts.user_id AND tenant_id = posts.tenant_id
  )
- UPDATE: USING で「自テナント所有の post を選ぶ」、WITH CHECK
  で「更新後も自テナント所属、かつ user との整合」
- DELETE: USING (tenant_id = ...)

  ▎ ヒント：USING と WITH CHECK の述語が同一になることが多いですが、コードの意図を表す
  ▎ ために両方明示的に書くことを推奨。WITH CHECK だけ省略すると、UPDATE で USING
  ▎ がコピーされる仕様（後述）に頼ることになり、読み取り時に意図が伝わりにくい。

  1. ポリシーの命名規則（あなたが決める）
  
  例：

  <table>_<command>_own_tenant
  例: posts_select_own_tenant
      posts_insert_own_tenant_with_user_check
      posts_update_own_tenant
      posts_delete_own_tenant

  12 個になります。命名は何でも良いですが、\dp
  で見たときに何のポリシーか分かるようにすること。

  app_user の動作確認のために、データを少し入れ直す

  pnpm db:reset 直後でデータが空のはずなので、postgres か migrator
  でテストデータを入れます：

  T1 = テナント 1
  T2 = テナント 2
  U1A = T1 のユーザー
  U1B = T1 のユーザー
  U2A = T2 のユーザー

  P2A = U2A が書いた T2 の post

  完了判定（最も大事）

  1. GUC 未設定でのエラー（判断 2A の動作確認）

  docker compose exec db psql
  "postgres://app_user:app_user_password@localhost:5432/rls_poc"
  
  SELECT * FROM posts;
  -- 期待: ERROR: unrecognized configuration parameter "app.tenant_id"
  
  → アプリ層が SET LOCAL を忘れたら、読めずに即エラーで発覚する。判断 2A の通りの挙動。

  1. T1 セッションでの可視性

  BEGIN;
  SET LOCAL app.tenant_id = 'T1 の UUID';

  SELECT *FROM tenants;       -- T1 の行 1 つだけ
  SELECT* FROM users;         -- U1A, U1B のみ（U2A は見えない）
  SELECT * FROM posts;         -- P1A のみ（P2A は見えない）

  COMMIT;

  1. T2 セッションでの可視性
  
  同様に app.tenant_id = T2 で：T2 のテナント、U2A、P2A だけ見える。P1A は見えない。

  1. 越境 INSERT の遮断（M1 で観察したやつが今度は止まる）

  T1 のセッションで：

  BEGIN;
  SET LOCAL app.tenant_id = 'T1 の UUID';

  -- 試みる: T1 を名乗りつつ、user_id は T2 の U2A
  INSERT INTO posts (id, tenant_id, user_id, title)
  VALUES (gen_random_uuid(), 'T1', 'U2A の UUID', 'cross-tenant post');
  -- 期待: ERROR: new row violates row-level security policy

  1. 自テナント INSERT の許可

  T1 のセッションで：

  INSERT INTO posts (id, tenant_id, user_id, title)
  VALUES (gen_random_uuid(), 'T1', 'U1A の UUID', 'normal post');
  -- 期待: 成功

  1. 越境 UPDATE の遮断（attack: 自テナント post を T2 に飛ばす）

  T1 のセッションで：

  UPDATE posts SET tenant_id = 'T2' WHERE id = 'P1A の UUID';
  -- 期待: ERROR: new row violates row-level security policy (WITH CHECK)
  -- もしくは UPDATE 0（USING で対象が見つからずスキップ）

  → どちらの結果になるかは USING と WITH CHECK の評価順次第ですが、T1 から T2
  への移動は防がれることが重要。

  1. FORCE の効果確認（B 選択の見せ場）
  
  migrator セッションで（migrator は所有者）：

  docker compose exec db psql
  "postgres://migrator:migrator_password@localhost:5432/rls_poc"

  SELECT * FROM posts;
  -- 期待: ERROR: unrecognized configuration parameter "app.tenant_id"
  -- → FORCE が効いている証拠（owner も RLS 適用対象）

  BEGIN;
  SET LOCAL app.tenant_id = 'T1 の UUID';
  SELECT * FROM posts;
  -- 期待: T1 の posts のみ
  COMMIT;
  
  → FORCE がなければ migrator は所有者として素通りで全件見えていたはず。FORCE
  が効いていることを目視できた瞬間が、判断 5A を選んだ最大の学習成果。

  postgres セッションでは SUPERUSER で素通り（FORCE も SUPERUSER
  を止められない）。これも確認できると、各属性の階層が腑に落ちる。

  詰まりやすいポイント
  
- FOR INSERT には USING を書かない：構文エラーになる。WITH CHECK のみ。
- FOR DELETE / FOR SELECT には WITH CHECK を書かない：構文エラー。
- FOR UPDATE で WITH CHECK を省略すると USING
  がコピーされる：仕様。意図を明示するため両方書くのを推奨。
- FORCE を入れ忘れると、migrator で接続したときに RLS が見えない。判断 5A
  の効果が観察できなくなる。
- __drizzle_migrations には RLS を入れない：migrator が migrate を実行するとき、自分
  の管理テーブルにアクセスできなくなり、デッドロック的なバグになる。3 テーブルだけに
  ENABLE。
- テストデータは適用前に入れる：適用後は migrator も SET LOCAL が必要になり、INSERT  
  が面倒。
- GUC 名前空間：app.tenant_id のように . を含む 2 セグメント名でないと PG
  が拒否します。
- トランザクション境界：SET LOCAL はトランザクション内のみ有効。BEGIN / COMMIT
  を使うか、psql 単発のセッションで SET（LOCAL
  なし）を使うか。後者だとセッション全体に残るので注意。

  コミット粒度の提案
  
  feat(db): enable RLS with per-command policies on tenants / users / posts

- ENABLE ROW LEVEL SECURITY + FORCE on all tenant-scoped tables
- 12 per-command policies (SELECT/INSERT/UPDATE/DELETE × 3 tables)
- posts INSERT/UPDATE WITH CHECK validates user_id-tenant_id consistency
    via subquery to prevent cross-tenant attribution attacks
- migrator and app_user are both subject to RLS due to FORCE
- Sessions must SET LOCAL app.tenant_id; missing GUC raises an error
    (per design decision: bugs surface immediately rather than silently)

feat(db): add dev seed with multi-tenant fixtures via docker bind-mount

- src/db/seeds/dev.sql: 2 tenants, 3 users (alice/bob in T1, carol in T2),
  3 internally-consistent posts. Cross-tenant attacks are exercised at
  runtime by app_user, not pre-loaded.
- docker-compose.yml: bind-mount src/db/seeds → /seeds:ro for psql -f access
- package.json: pnpm db:seed runs psql as postgres SUPERUSER, bypassing RLS
  during fixture loading
- Seeds are explicitly outside the drizzle-kit migration pipeline so they
  never run in production deploys
