# M6: 破壊テスト

## 狙い

M5 までで「**正常系で** RLS + `withTenant` + middleware が機能する」ことを示した。
M6 では「**敵対的入力 / 設定ミス / 直接攻撃** のもとでも破綻しない」ことを自動テストで
証明する。

`M5.md` の完了判定にあった curl 8 シナリオは手動チェック。M6 でそれを自動化したうえで、
さらに守備範囲を広げる。

## テスト戦略

3 サブマイルストンに分割。**ランナーを使い分ける**ことで「同プロセス内の高速ユニット」
と「実プロセス越しの黒箱」を別レイヤで検証する。

| サブマイルストン | 範囲 | ランナー | ファイル |
| --- | --- | --- | --- |
| M6-A | HTTP 層の越境攻撃マトリクス | Playwright (`request`) | `tests/e2e/cross-tenant.spec.ts` |
| M6-B | RLS failsafe（`withTenant` 不使用時の防御） | vitest (実 PG 経由) | `tests/security/rls-failsafe.test.ts` |
| M6-C | `x-tenant-id` ヘッダ攻撃面 | vitest (`app.request`) | `tests/security/header-attack.test.ts` |

Newman は導入を見送った（理由: テストは TS で書かれており Playwright と完全に守備範囲が
重なる。3 場所メンテナンスは投資対効果が悪い。詳細は本セッションのログ参照）。

## M6-A: 越境攻撃マトリクス（Playwright）

`pnpm start` で起動した Hono サーバに対し、Playwright の `request` フィクスチャから
本物の HTTP を投げる。各テストは `beforeEach` で seed リセットして独立性を保つ
（`workers: 1`, `fullyParallel: false`）。

### 攻撃シナリオ

| 攻撃 | 期待 |
| --- | --- |
| T1 で `GET /posts/:T2id` | 404 `not-found`（存在隠蔽） |
| T1 で `PUT /posts/:T2id` | 404 |
| T1 で `DELETE /posts/:T2id` | 404 |
| T1 で `userId=T2_user` を `POST /posts` | 400 `cross-tenant-violation`（pg 42501） |
| `POST` body に余計な `tenantId: T2` を仕込む | 201、結果は T1 として作られる（zod strip） |
| 上記攻撃 volley の後、T2 視点で `GET /posts` | 集合が seed と一致（無傷） |
| エラー応答全般 | `Content-Type: application/problem+json` |

### Playwright 設定の要点

- ブラウザ非依存（API テストのみなのでブラウザバイナリのインストール不要）
- `webServer.url: '/health'`（200-399 を ready 判定）
- ローカルでは既存サーバ再利用、CI では fresh に起動
- グローバル seed は `tests/e2e/global-setup.ts`、各テスト前 reseed は
  `tests/e2e/helpers/seed.ts` の `reseed()` ヘルパ

## M6-B: RLS failsafe（vitest）

> 開発者が `withTenant` を呼ばずに `app_user` で生クエリを叩いたら？

`pg.Pool` を直接使い、`withTenant` を経由しないシナリオを再現する。`app_user` での接続
であることが前提なので、RLS は常時アクティブ。

### シナリオと期待

| 操作 | `app.tenant_id` | 期待 |
| --- | --- | --- |
| `SELECT` | 未設定 | `unrecognized configuration parameter` で raise |
| `INSERT` | 未設定 | 同上で raise |
| `UPDATE` | 未設定 | 同上で raise |
| `DELETE` | 未設定 | 同上で raise |
| `INSERT` (tenant_id=T2) | `set_config(T1)` | 42501 (`WITH CHECK` 違反) |
| `INSERT` (tenant_id=T1, user_id=T2_user) | `set_config(T1)` | 42501（policy の EXISTS 副条件で防御） |
| `UPDATE` (T2 の行) | `set_config(T1)` | 0 行更新 |
| `DELETE` (T2 の行) | `set_config(T1)` | 0 行削除 |
| `SELECT count(*)` | `set_config(T1)` | 2（対照：自テナントは見える） |

### 設計上の核

- ポリシーは厳格モード `current_setting('app.tenant_id')::uuid`（第 2 引数なし）。
  未設定時に **silent な空集合** ではなく **明示的な raise** にすることで、
  `withTenant` 呼び忘れがテストとログで即座に発覚する。

## M6-C: ヘッダ攻撃面（vitest）

既存の `tests/middleware/with-tenant.test.ts`（基本 4 ケース）を補完する境界条件と
攻撃シナリオ。

| 入力 | 期待 |
| --- | --- |
| 空文字列 | 401 `TENANT_HEADER_MISSING`（不在扱い） |
| 内部に空白を含む UUID | 400 `VALIDATION_ERROR` |
| SQL injection 風 payload | 400 `VALIDATION_ERROR`（DB 到達前） |
| version 桁 0 の UUID | 400 |
| 重複 `x-tenant-id` ヘッダ | カンマ結合され uuidv7 失敗 → 400 |
| 1 文字落としの UUID | 400 |
| hex 範囲外文字（g-z）混入 | 400 |

注: 前後の OWS（optional whitespace）は HTTP RFC 7230 で trim される仕様なので、
本実装でテストすべきは「内部に紛れ込んだ空白」のほう。

## スコープ外

PoC のサイズに対して投資対効果が悪いので意図的に除外：

- DB 接続喪失時の挙動（運用テスト）
- プール枯渇 / コネクション漏れ
- DEADLOCK / serialization failure の再現
- 大容量 body / slow loris 系の DoS
