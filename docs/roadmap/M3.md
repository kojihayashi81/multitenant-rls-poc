# M3: RLS の有効化とコマンド別ポリシー

## 狙い

`tenants` / `users` / `posts` の 3 テーブルに **`ENABLE` + `FORCE ROW LEVEL SECURITY`**
を入れ、各テーブルに **コマンド別の 4 ポリシー（SELECT / INSERT / UPDATE / DELETE）**
を貼る。`app_user` セッションで `SET LOCAL app.tenant_id = ...` を行ってからクエリすると、
**自テナントの行しか見えず、越境 INSERT/UPDATE はすべて DB レベルで弾かれる** 状態を作る。

このマイルストンの最大の見せ場は、M2 で別ロールに移譲した `migrator`（テーブル所有者）
が `FORCE` のおかげで RLS を**バイパスできない**ことを観察できる点。

## 事前知識：`USING` と `WITH CHECK` の役割

| コマンド | `USING` | `WITH CHECK` |
| --- | --- | --- |
| `SELECT` | 既存行に対して可視判定 | — |
| `INSERT` | — | 新規行に対して書き込み可否を判定 |
| `UPDATE` | 既存行に対して更新対象になり得るか判定 | 更新後の行が条件を満たすか判定 |
| `DELETE` | 既存行に対して削除対象になり得るか判定 | — |

`UPDATE` には両方が登場する。**「どの行を選んで」「どんな状態に変えてよいか」** の二段階判定。

論理合成の例（`PERMISSIVE` は OR、`RESTRICTIVE` は AND）：

```text
PERMISSIVE  P1: tenant_id = current_setting('app.tenant_id')::uuid
PERMISSIVE  P2: visibility = 'public'
RESTRICTIVE R1: deleted_at IS NULL

→ 読める行 = R1 AND (P1 OR P2)
            = deleted_at IS NULL
              AND (tenant_id = ... OR visibility = 'public')
```

## 採用した設計判断

| # | 判断 | 採用 | 理由 |
| --- | --- | --- | --- |
| 1 | テナントコンテキストの GUC キー名 | `app.tenant_id` | PostgreSQL 慣習の `app.` prefix が「アプリ独自設定」を示す。`.` 区切りは custom GUC で必須 |
| 2 | GUC 未設定時の挙動 | A: エラーで顕在化 + C: アプリ層で必ず注入 | `current_setting()` 第 2 引数を付けず厳格モードで参照。`withTenant` 呼び忘れが silent な空集合返却ではなくラウドな例外として即発覚する |
| 3 | ポリシーの粒度 | コマンドごとに 4 ポリシー（合計 12） | `FOR ALL` の 1 本にまとめると行数は減るが、「どのコマンドで何が違うか」がコードで読めなくなる。`INSERT` には `USING` が無視される / `DELETE` には `WITH CHECK` が無視されるという仕様をコメントで補強する代わりに、構文として明示的に分ける |
| 4 | `tenants` テーブルへの RLS | A: 自テナントの行のみ可視 | PoC として最小。テナント追加を運用 API から閉め出すなら B（INSERT 禁止）にする選択肢もある |
| 5 | `FORCE ROW LEVEL SECURITY` の付与範囲 | 全 3 テーブルに付与 | `migrator` でも RLS が効くことを観察できる。M2 で 3 ロール構成にした最大の意義はここ |

## 0003_enable_rls.sql の構成

12 ポリシー + 6 `ALTER`（3 テーブル × `ENABLE` + `FORCE`）。

### `ENABLE` + `FORCE`

```sql
ALTER TABLE <name> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <name> FORCE ROW LEVEL SECURITY;
```

3 テーブルすべてに対して。`FORCE` を**書き忘れると、`migrator` 接続のときに RLS が
バイパスされる**（テーブル所有者だから）。判断 5 の効果が観察できなくなる。

### `tenants` のポリシー（4 つ）

`tenants` は `id` 列がそのままテナント識別子（`tenant_id` 列を持たない）。

```sql
-- SELECT
USING (id = current_setting('app.tenant_id')::uuid)

-- INSERT
WITH CHECK (id = current_setting('app.tenant_id')::uuid)

-- UPDATE
USING       (id = current_setting('app.tenant_id')::uuid)
WITH CHECK  (id = current_setting('app.tenant_id')::uuid)

-- DELETE
USING (id = current_setting('app.tenant_id')::uuid)
```

すべてのポリシーに `TO app_user` を付ける（`migrator` は所有者として `FORCE` 経由で
RLS にかかるが、ポリシー自体は `app_user` を対象に書く方針。`migrator` 用ポリシーは
作らない）。

### `users` のポリシー（4 つ）

述語は `tenants` と同じ形だが、参照する列は `tenant_id`：

```sql
USING / WITH CHECK: tenant_id = current_setting('app.tenant_id')::uuid
```

### `posts` のポリシー（4 つ、最も慎重）

`SELECT` / `DELETE` は素直：

```sql
USING (tenant_id = current_setting('app.tenant_id')::uuid)
```

**`INSERT` / `UPDATE` は越境 attribution 攻撃を遮断するため `EXISTS` 副条件を入れる**：

```sql
WITH CHECK (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND EXISTS (
      SELECT 1 FROM users
      WHERE id = posts.user_id AND tenant_id = posts.tenant_id
    )
)
```

これがないと、攻撃者は **「自テナント名義 (`tenant_id = T1`) で投稿しつつ、`user_id`
だけ他テナントのユーザ (`U2A@T2`) を指す」** 形のレコードを作れてしまい、ログ・通知・
監査などで attribution が壊れる。`users` テーブル側で `posts.user_id` の所属テナント
が `posts.tenant_id` と一致することを副条件で確認することで、この攻撃を防ぐ。

`UPDATE` の `USING` にも同じ `EXISTS` 副条件を入れている（更新対象の選択時点で
attribution 整合をチェック）。

## テストデータは M3 適用前に投入する

`pnpm db:reset` 直後でデータが空の状態から、`postgres` か `migrator` で fixture を
入れる。**M3 適用後は `migrator` も `FORCE` で RLS の対象**になり、`SET LOCAL
app.tenant_id` なしでは `INSERT` も `SELECT` もできなくなるため、運用上面倒になる。

M3 では暫定的に手動 fixture でも良いし、後続の M4 直前に `src/db/seeds/dev.sql` を
書いて `pnpm db:seed`（postgres SUPERUSER で `RLS` をバイパスして流す）に切り替える。

## 完了判定（psql で確認）

`app_user` 接続で：

| # | シナリオ | 期待 |
| --- | --- | --- |
| 1 | GUC 未設定で `SELECT * FROM posts` | `ERROR: unrecognized configuration parameter "app.tenant_id"`（判断 2A の挙動） |
| 2 | `SET LOCAL app.tenant_id = T1` の中で SELECT | `tenants` は T1 の 1 行、`users` は U1A/U1B、`posts` は P1A のみ |
| 3 | `app.tenant_id = T2` で同様 | T2 / U2A / P2A のみ。P1A は見えない |
| 4 | T1 セッションで `tenant_id=T1, user_id=U2A` の越境 INSERT | `ERROR: new row violates row-level security policy` |
| 5 | T1 セッションで `tenant_id=T1, user_id=U1A` の正規 INSERT | 成功 |
| 6 | T1 セッションで自分の post の `tenant_id` を T2 に書き換える UPDATE | RLS 違反で拒否（`WITH CHECK` または `USING` で 0 行） |

`migrator` 接続で：

| # | シナリオ | 期待 |
| --- | --- | --- |
| 7 | GUC 未設定で SELECT | 判断 2A の通り `unrecognized configuration parameter`（**`FORCE` の効果**） |
| 8 | `SET LOCAL app.tenant_id = T1` で SELECT | T1 の post のみ。所有者であってもバイパスできない |

`postgres`（SUPERUSER）は `FORCE` も止められないので素通りで全件見える。
**SUPERUSER / BYPASSRLS 属性の不可侵性** は設計時に意識して使い分けるべき。

## 詰まりやすいポイント

- `FOR INSERT` には `USING` を**書かない**（構文エラー）。`WITH CHECK` のみ。
- `FOR DELETE` / `FOR SELECT` には `WITH CHECK` を**書かない**（構文エラー）。
- `FOR UPDATE` で `WITH CHECK` を省略すると `USING` がコピーされる仕様。意図を明示するため両方書く。
- `FORCE` を入れ忘れると `migrator` で RLS が見えなくなり、判断 5A の効果が観察できない。
- `__drizzle_migrations` には RLS を**入れない**（`migrator` 自身の管理テーブルなので、入れると `migrate` 自体が止まる）。
- GUC 名前空間：`app.tenant_id` のように `.` を含む 2 セグメント名でないと PG が拒否する。
- `SET LOCAL` はトランザクション内のみ有効。`BEGIN` / `COMMIT` で囲うか、psql のセッション全体に効く `SET`（LOCAL なし）を使うかは意識する。後者は次のリクエストに漏れる危険があるが、psql の手動実験では便利。

## このマイルストンで得られた言語化

- **`ENABLE` と `FORCE` の差**：`FORCE` がなければ所有者は RLS をバイパス。3 ロール構成で `migrator` を所有者にしたからこそ、`FORCE` の必要性を観察できる。
- **`SUPERUSER` と `BYPASSRLS` の不可侵性**：`FORCE` でも止められない。設計で `SUPERUSER` を運用に使わない理由になる。
- **GUC 厳格モード**：`current_setting()` 第 2 引数を付けないことで「未設定 = ラウドに失敗」を選んだ。silent な空集合返却よりバグが見つかる。
- **越境 attribution の遮断**：`WITH CHECK` のサブクエリで隣接テーブルとの整合性を取れる。`posts.user_id` と `posts.tenant_id` の整合は `users` テーブルを参照して確認。
- **コマンド別ポリシーの可読性**：12 行になるが、`\dp` や migration ファイルを読めば「どのコマンドに何の制約があるか」が一目で分かる。
- **`SET LOCAL` のトランザクション scope**：M4 でアプリから注入する際の前提知識。プール再利用と相性が良い。
