  M3-2：設計判断（あなたが選ぶ）

  判断 5 つあります。各選択肢のトレードオフを示します。

  判断 1：テナントコンテキストの命名

  current_setting('app.tenant_id') のような GUC 変数のキー名。

  - A. app.tenant_id：シンプル。"app." prefix は PostgreSQL
  の慣習で「アプリ独自の設定」を示す
  - B. app.current_tenant：より読みやすい
  - C. rls.tenant_id：RLS 専用と分かる名前

  ▎ プレフィックスは custom GUC では必須（PG が . でドメインを区切ることを期待する）。A
  ▎  が一番慣習に従っています。

  判断 2：セッションが未設定のときの挙動

  ポリシー述語で current_setting('app.tenant_id') を呼んだとき、未設定だと PG
  はエラーを投げる：

  ERROR: unrecognized configuration parameter "app.tenant_id"

  - A. エラーで落ちるのを許容：未設定のセッションは「事故」だとして即座に発覚させる。最
  も安全
  - B. デフォルト値（'' 等）を与えてエラーは出さない：current_setting('app.tenant_id',
  true) 第 2 引数 true で missing を許可、NULL を返す。ポリシー述語側で tenant_id =
  NULL（NULL 評価で何も見えない）にする
  - C. アプリ層で必ず SET LOCAL を保証する：DB
  側のフォールバックは置かない、アプリ層のミドルウェアでガード

  ▎ A + C がよく組み合わされます。「DB 側はガードを置かない、アプリ層で確実に注入する、
  ▎ 注入忘れは事故として顕在化させる」というスタンス。

  判断 3：ポリシーの粒度

  各テーブル（tenants / users / posts）に：

  - A. 1 つの FOR ALL ポリシーで USING + WITH CHECK 両方を定義：シンプル、行数少ない
  - B. SELECT / INSERT / UPDATE / DELETE ごとに分けて 4  
  つのポリシー：明示的、各コマンドで何が違うかコードで読める
  - C. SELECT は別、書き込み系は ALL でまとめる：実用的な中間

  ▎ A が最少コードだが、「INSERT には USING が無視される」「DELETE には WITH CHECK
  ▎ が無視される」という事実をコメントで補強する必要あり。B
  ▎ は冗長だが、応募リポではコードが教科書的に読めるので強いシグナル。

  判断 4：tenants テーブルへの RLS

  tenants 自体には何を求めますか？

  - A. RLS 適用、自テナントの行のみ可視：「自分のテナント情報だけ見える」
  - B. RLS 適用、ただし可視は OK / INSERT
  は禁止：テナント追加はバックオフィス管理者だけ（migrator や別ロール経由）
  - C. RLS 適用しない：tenants は全員から読み取り可能、ただし RLS
  がないので操作も全員可（危険）

  ▎ A が最小。B は「テナント追加はアプリ経由でやらない」という運用が前提なら自然。POC  
  ▎ として A で進めても OK。

  判断 5：FORCE ROW LEVEL SECURITY を入れる位置

  判断 3 の M2 で「FORCE を付ける」と決めました。これを：

  - A. 全テナントテーブルに一律付与：tenants / users / posts すべてに FORCE
  - B. 特に守りたいテーブルだけに付与：例えば posts のみ
  - C. 付けない：FORCE は今回は省略、migrator 接続でも RLS
  が見えなくする学習体験を優先しない

  ▎ 判断 1 のロール 3 ロール化を選んだ最大の見せ場は、FORCE があれば migrator
  ▎ セッションでも RLS が効く、を観察できること。A で全部に付ける、または B +
  ▎ 比較表で「テーブル別に挙動が変わるのを見る」も学習価値あり。
